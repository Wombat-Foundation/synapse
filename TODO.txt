Findings, then the actual debate.

Continuwuity's state_hamt (already in prod use):
- src/service/rooms/state_hamt/store.rs — a Store wrapping a RocksDB Map, keyed purely by StructuralHash, point-lookup only, with an in-process moka cache. No range use of the HAMT CF itself.
- state_accessor/state.rs has state_full_hamt / load_full_state_hamt — full-state reads walk the entire HAMT tree. There's no typed/per-event-type subtree split — every full-state read (send_join, /state, sync full-state) pays the whole-tree walk, not just the changed subtree.
- They already keep a separate shortstatekey_statekey / statekey_shortstatekey pair of ordered CFs to intern keys, but that's for compactness, not for bulk-by-type range scans.

So the typed-root commit we just made (5f72de8918) is something continuwuity doesn't have yet — a real point where ./ can end up ahead: state_full_hamt for m.room.member only would traverse one subtree instead of the whole tree.

SQL vs TiKV — my actual read:

Don't split effort. Focus on TiKV, for reasons visible directly in the code, not abstractly:

1. Continuwuity's design is the proof of concept, and it's built entirely on an embedded ordered byte-keyed KV (RocksDB), not SQL. The HAMT nodes, the shortkey interning, everything — all live as CFs with insert(key_bytes, value_bytes) and no joins. TiKV is that same shape (ordered byte KV) distributed. Porting the design there is nearly 1:1 — same key layout, same PersistedInternalNode encode/decode, same point-lookup CF semantics rust side already has via rezzy::hamt.
2. SQL forces the split we hashed out earlier: HAMT nodes as an opaque point-lookup table, plus a separate relational/persistent-tree structure to get ordered range scans back, because Postgres/SQLite can't range-scan inside serialized blobs. That's a second engine to build and keep consistent — essentially reimplementing what TiKV/RocksDB gives for free via ordered CFs.
3. This repo already carries the TiKV plumbing (fde71deb77 ci: add TiKV to trial test matrix, 4baf3e6e56 sytest-tikv networking) — the infra investment is already sunk in that direction, unlike a new SQL schema.
4. SQL (Postgres) still matters as the default/compat backend most deployments run — but the honest scope there is "flat state_hamt_nodes point table + accept O(S) tax on full materialization, or don't put the HAMT experiment there at all yet." Don't try to make Postgres do ordered range scans over HAMT structure; that's the trap we mapped out above.

Net: put the typed-root / bulk-query design energy into the TiKV backend where it's a natural fit and matches continuwuity's validated architecture; keep SQL as the plain point-lookup fallback rather than building a second persistent-tree engine on top of it.

❯ btw if we have to bulk update every event id under a root, or theoretically partially or partition-based sieving or segment-based rebuilding, how would we accomplish that without tons of writes?

Depends on what "bulk update every event id" actually means — the answer differs by a lot:

Case 1: it's a remap, not a content change (e.g. renumbering short_event_ids, backfill compaction,

Don't touch the tree at all. Add a level of indirection between the HAMT leaf and the thing you're bulk-updating:

HAMT leaf:  state_key -> surrogate_id      (stable, never touched by the remap)
side table: surrogate_id -> event_id       (small, mutable, this is what changes)
If the HAMT stores event_id directly as the leaf value, remapping every event_id forces every leaf every ancestor hash to change — genuinely O(S) node writes, no way around it in a purecontent-addressed tree. Breaking that coupling means the bulk update becomes a swap of one small tap is itself a deterministic function you can apply at read time — e.g. a generation/epoch tag
consulted during lookup instead of rewritten per row).

Case 2: it's actually scoped to a subset (partition/segment/sieve)

This is the general case the typed-root commit is a special case of. Generalize the directory pattern:

root
 └── directory: partition_key -> subtree_hash

where partition_key is whatever you're segmenting on (event type, as landed; or a hash-prefix shardention bucket — anything with a stable, computable key). Rebuilding one segment:

- touched partitions: rebuild their subtree (O(k log s) where k/s are just that partition's changed
- untouched partitions: their subtree hash is copied into the new directory unchanged — zero writest partition is

This is the actual lever against "tons of writes": partition granularity determines your write floo(many small subtrees) means a bulk op touching 3 of 200 partitions writes ~1.5% of the tree insteadof the whole thing. build_hamt's structural dedup already gives you this for free at the node level, but explicit partitioning gives it to you at the directory level too, so you don't even have to walk untouched subtrees to know
they're unchanged.

Case 3: sieving/filtering is read-only

If "sieve" just means "select the subset matching a predicate," that's a traversal, not a write. Noalk it, and if the predicate aligns with a partition key (e.g. "all m.room.member") skip whole
subtrees via the directory instead of visiting every leaf. Cost is O(matched + directory entries sk

Case 4: genuinely every leaf's content changes with no valid indirection
 Then O(S) writes is the actual lower bound — you can't produce S different values without S writes.mechanical: batch them into one WriteBatch/TiKV transaction so it's O(S) writes but O(1) round trips, and let build_hamt's dedup catch any leaves that happen to end up unchanged after the transform (if1 changed, this still saves real work).

The practical takeaway: before reaching for case 4, check whether the "every event_id" requirement ion (case 1) or whether the update is actually partition-scoped and just needs a directory (case 2) — most things that sound like "bulk update everything" turn out to be one of those.
